Unlock Functionality — Database Runbook

The unique unlock identity is matches.matchid. It is an integer and must be passed as MatchId throughout the match/confirmation/reveal flow.

Tables to check, in sequence

2revealsIdempotency check. If a row already exists for the match, contacts are already unlocked and no further credit may be deducted.match_id (unique), revealed_at

Unlock sequence

Column rule: use matches.state as the canonical dual-confirmation lifecycle. Do not overwrite matches.status with pending_confirmation or confirmed. The existing status column belongs to the matching/listing lifecycle and should remain available for its existing meaning.

  1. Load the match.
    Read matches by matchid = :matchId. The requesting broker must equal either listing_broker_id or requirement_broker_id.
  2. Prevent duplicate charging.
    Read reveals by match_id. If it exists, return the previously unlocked result; do not insert anything and do not deduct credits.
  3. First broker confirms.
    Upsert one row in match_confirmations; set all checklist fields, confirmed_at = now(), and window_expires_at = now() + 4 hours. Update matches.state to pending_confirmation; leave matches.status unchanged.
  4. Second broker confirms.
    Upsert their confirmation row with the same 4-hour window. Check that both expected broker rows have non-null, non-expired confirmed_at values.
  5. Confirm the match.
    If both confirmations pass, update matches.state to confirmed; leave matches.status unchanged.
  6. Check both wallets.
    Read both credit_wallets rows. Each broker needs at least one combined free/paid credit. If either broker lacks credit, stop: no reveal and no deductions are written.
  7. Reveal atomically.
    Within one database transaction, insert one reveals row, decrement each wallet (free credits first), and insert both ledger rows in credit_transactions. Commit only when all writes succeed.
  8. Return contact information.
    Read the other broker from brokers and return their name and phone to each party.

Frontend state to show

The frontend should treat state as the handshake state and reveals.match_id as the final unlock flag. A match may remain state = 'confirmed' after contacts are revealed; that is correct.

API/database conditionShow to the current brokerPrimary action
state = 'matched'; no confirmation row for current brokerNew match / not confirmedConfirm & Connect
state = 'pending_confirmation'; current broker has a confirmationWaiting for other brokerDisabled button; show expiry time
state = 'pending_confirmation'; current broker has no confirmationOther broker wants to connectConfirm & Connect
state = 'confirmed'; no reveals rowBoth confirmed; reveal pending / insufficient creditShow credit-purchase or retry guidance
A reveals row exists for match_idUnlockedShow counterparty name and phone
state = 'expired'Confirmation window expiredConfirm & Connect again

Do not use status to decide which confirmation button or banner to render. Return state, current-broker confirmation status, window_expires_at, and isRevealed in the match API response. This avoids relying on the frontend to infer state from other broker data.

Successful reveal: data written

OrderTableOperation
1match_confirmationsInsert or update broker A confirmation.
2matchesUpdate state to pending_confirmation; do not change status.
3match_confirmationsInsert or update broker B confirmation.
4matchesUpdate state to confirmed; do not change status.
5revealsInsert one row: match_id, revealed_at.
6credit_walletsUpdate broker A balance and updated_at.
7credit_transactionsInsert broker A deduction: type = 'deduct', amount = 1, reference_type = 'reveal'.
8credit_walletsUpdate broker B balance and updated_at.
9credit_transactionsInsert broker B deduction with the same reveal reference.

Important: steps 5–9 are one transaction. A failed wallet check or write must roll back all of these steps.

Useful verification queries

-- Replace :match_id with the matches.matchid being investigated.
SELECT matchid, listing_broker_id, requirement_broker_id, state, status
FROM matches WHERE matchid = :match_id;

SELECT * FROM match_confirmations WHERE match_id = :match_id ORDER BY broker_id;
SELECT * FROM reveals WHERE match_id = :match_id;

SELECT broker_id, free_credits_balance, paid_credits_balance, updated_at
FROM credit_wallets
WHERE broker_id IN (
  SELECT listing_broker_id FROM matches WHERE matchid = :match_id
  UNION
  SELECT requirement_broker_id FROM matches WHERE matchid = :match_id
);

SELECT broker_id, type, amount, balance_after, reference_type, reference_id, created_at
FROM credit_transactions
WHERE notes = 'Reveal for match ' || :match_id
ORDER BY created_at;
